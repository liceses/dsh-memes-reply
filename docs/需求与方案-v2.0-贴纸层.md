# dsh-memes-reply · 需求与方案 v2.0（贴纸层：会话流里的派生节点）

> 前置：`docs/需求与方案-v1.0.md`（§12–§15 记着 B-auto、挂件、气泡角，以及那两次"尾巴座位被 `present` 交付卡片抢走"的事故）
> 本文只写**本轮敲定的需求**与**选定路径的设计**。决策来源：本轮 6 个问答。

---

## 0. 本轮用户反馈 → 决策锁定

用户原话：

1. 「meme 贴纸不会动」
2. 「贴纸不是跟着会话走的」
3. 「我想要的是**内联的逻辑的贴纸版**：每个对话回复一个表情，plus 输出中也有表情」

| # | 问题 | 你的选择 | 由此产生的约束 |
| --- | --- | --- | --- |
| D1 | 「跟着会话走」 | **贴在对应那条回复旁边就行，刷新/滚回去也要在（不必进正文文本）** | 必须是**会话流里的持久物**，但**不许污染消息文本**（否掉"往正文注入 markdown"的内部路线） |
| D2 | 「输出中也有表情」 | **生成中先显示「思考/打字中」专用表情，写完后换成这一轮的最终表情（前一张消失）** | 需要**两阶段**：一轮 = 同一个位置先占位后落定。"前一张消失"必须是结构性的，不能靠 CSS 遮掩 |
| D3 | 常驻挂件 | **保留**（"我就是要随时能看到大肥鱼"） | 挂件与"这条回复的贴纸"是两个职责，互不替代、互不打架 |
| D4 | 频率 | **以回合为准：一问一答只在最终回复贴一张** | 中间步骤（工具调用那几步）不贴；一轮 = 一张 |
| D5 | 形态 | **复刻效果图：圆贴纸压在回复气泡右下角，悬停放大、点击看大图** | 沿用现有 `bubble` 的观感与交互 |
| D6 | 路径 | **A 派生节点（一次到位）** | 见 §3；先跑 §4 的探针，再动代码 |

## 1. 诊断：三条反馈对应的机制原因（都带证据）

| 现象 | 机制原因 | 证据 |
| --- | --- | --- |
| **不会动** | 贴纸的两个主力落点渲染的是**首帧静态缩略图**（thumb 本来是给设置面板预览墙省流量用的） | `src/client/bubble.tsx:63`：`matched.thumb ?? matched.url`；`src/client/fallback.tsx:199` 同款。只有 `src/client/pet.tsx:198` 展开态用 `item.url`（会动） |
| **不跟着会话走（一）** | 主力座位 `conversation.chat.turnTail` 是**竞争链**，本条目 `priority: 10` 排在官方 `present` 交付卡片（0）之后 → **凡是回复里提到文件路径的回合，尾巴被交付卡片接走，贴纸根本不渲染** | `src/client/index.tsx:129-150`；v1.0 §15.2 表第 4 行是真事故记录 |
| **不跟着会话走（二）** | 抢不到尾巴时走 `fallback`：`shell.overlay` 的**全站浮层**，固定屏幕位置、`fallbackSeconds` 后自己消失；绑定只存在**内存仓**里，刷新即空 | `src/client/fallback.tsx`、`src/store.ts`（纯内存 + TTL）、`src/client/poller.tsx`（800ms 轮询 `/auto/pending`） |
| 每轮一张其实有 | `autoMode: every` 一直在正常发布 | `~/.dsh/settings.yaml`：`dsh-memes-reply: {form: sticker, autoMode: every}`；`state.json` 里 18 个会话都有 `recent` 记录 |

**一句话**：贴纸功能"做出来了但没长在会话上"——它长在了浮层和一条随时被抢走的座位上。

## 2. 需求（v2.0）

### 2.1 功能需求

| ID | 需求 | 验收方式 |
| --- | --- | --- |
| FR1 | **每回合一张**：每个"一问一答"的**最终助手回复**下方/角上有一张贴纸；中间步骤（工具调用轮）不贴 | 连问 5 轮，5 张、位置各自对应自己的回复 |
| FR2 | **跟着会话走**：贴纸是那条回复的附属物 —— 向上滚回历史能看到、刷新页面还在、切到别的会话各是各的 | 滚动/刷新/F5 后逐条核对；两个会话互不串台 |
| FR3 | **会动**：渲染动画本体（全尺寸动画 WebP），**任何路径都不得再退回首帧静态图** | 肉眼可见循环播放；DOM 里 `src` 指向全尺寸路由而非 `/thumb/` |
| FR4 | **两阶段**：回合进行中显示「思考中 / 打字中」表情；该回合落定后**同一位置**换成这一轮的最终贴纸，**前一张消失**（不是并存、不是遮住） | 长回合（多次工具调用）全程盯屏：先占位动画，落定瞬间替换 |
| FR5 | **形态**：复刻效果图 —— 圆贴纸压在助手气泡右下角，悬停轻微放大，点击看大图（新窗口） | 与 v1.0 §14 的效果图逐项对照 |
| FR6 | **常驻挂件保留**：右下角可拖/可换/可收起的挂件不受本次改动影响，仍是"随时能看到" | 挂件功能回归测试 |
| FR7 | **宿主状态仍生效**：总开关 `enabled`、会话静音 `/fish off`、冷却（不连贴同一张）、面板"下一轮用这张"、模型工具 `use_sticker` 的选择，在新架构下语义不变 | 逐项操作可见 |
| FR8 | **可观测**：沿用现有 `trace`（host 决策 + 客户端回执双向缓冲），`/stats` 一次读全；新增的渲染点必须有"到底渲染了没"的回执 | `/stats` 能看到本轮的决策来源与渲染回执 |

### 2.2 非功能需求

| ID | 需求 | 理由 |
| --- | --- | --- |
| NFR1 | **不写会话日志**：本方案不向 session log 追加任何自定义事件类型 | 见 §3.4，这是硬约束（会毁日志可读性） |
| NFR2 | **不引入轮询/SSE**：贴纸的显示不再依赖"宿主先发事件、客户端后取"的时序 | 消灭 v1.0 §15 那一整类"赶不上渲染"的竞态 |
| NFR3 | **刷新即重放**：状态是会话事件的纯函数，`F5` 后看到的贴纸与刷新前逐条一致（确定性） | 同一 `(sessionId, turn)` 必须推出同一张 |
| NFR4 | **性能**：同屏多张动画的内存与带宽要记账（限制显示尺寸、不可见时暂停播放或退化为静态帧） | 素材是 85.9MB / 均值 560KB 的动画 WebP |
| NFR5 | **停用即净**：节点定义、槽位注册、样式全部由 `ctx.effect` 持有；卸载后界面回到官方原样 | 与 v1.0 NFR4 一致 |

## 3. 方案 A：会话流里的**派生节点**

### 3.1 座位与机制（都是查过源码的事实）

| 事实 | 出处 |
| --- | --- |
| 客户端插件可注册**自己的会话节点定义**：`ctx.uiConversation.events.register(definition)` | `@deepseek-ai/dsh-client-ui-conversation/client` → `conversation/event-registry.d.ts`；官方 `dsh-client-ui-deliverables` 就是这么做的 |
| 定义契约：`{ kind, target?, match(event), start(), update(), publication?, buildLocationData?, buildViewNode? }` —— 一台"会话事件 → 节点状态"的状态机 | `contract/conversation.d.ts`（`ConversationNodeDefinition`） |
| 定义可出版**自己的视图节点**（`buildViewNode` → `target` 声明），渲染进会话流 | 同上；ui-chat 自己的 assistant/tool/turn-tail 定义都是 `target: 'chat'` |
| 渲染座位是 **keyed** 的 `conversation.chat.node`，`ChatNodeDataMap` 是**可合并扩展**的（所以插件能新增自己的 kind） | `dsh-client-ui-chat/client` → `contract/chat-nodes.d.ts`（"Merge-extensible payload registry"）、`contract/slots.d.ts` |
| 节点顺序由 **anchorSeq** 决定，官方已经为"助手消息之后的补充节点"留了位置：`CHAT_SYNTHETIC_SEQ_OFFSETS.finalizedFollowup = 0.1` | `conversation-nodes/common.d.ts` |
| `turn/start` / `turn/end` 等边界事件对定义可见（deliverables 的 `match` 就是认 `turn/start`） | deliverables 的 `deliverablesDefinition.match` |

⇒ **贴纸可以成为会话流里的一条普通节点**：它跟着消息走、按会话隔离、由会话日志重放、可以被 `anchorSeq` 精确安排在某条回复下面。这正是 D1 要的"内联的逻辑"，而且是**客户端渲染**，所以形态、尺寸、动效完全可控（D5），也天然能表达"运行中 → 已落定"（D2）。

### 3.2 一轮一节点，两阶段

```
turn/start ──► 节点建立，state.phase = 'thinking'
               锚点跟着流式内容下移 → 显示「思考中/打字中」动画（sikao / dazi 系列）
                    │
assistant/message（本回合的收尾回复落定）
                    ▼
             state.phase = 'settled'，state.sticker = 派生出的一张
                    → 同一节点换图（思考那张消失，最终贴纸出现）
```

- **一个节点**、两次状态：D2 的"前一张消失"是**结构性**的，不需要藏、不需要等 TTL、不存在两张并存。
- 中间步骤（工具调用那几步）**不新增节点**：D4 的"以回合为准"直接落在 `match` 上。
- 「思考/打字」占位素材**现成**：`sikao`（正在思考 · 思考中/加载中）、`dazi`（打字 普通 · 打字中/输出中），另有 `sikao-renzhen`/`sikao-zixin`/`dazi-shengqi`/`dazi-naonu` 可做轮换。

### 3.3 数据从哪来：**纯客户端派生**（这是本方案最关键的简化）

节点状态只从**客户端已经有的东西**推：

| 输入 | 来源 | 用途 |
| --- | --- | --- |
| 轮次边界、收尾助手消息 | 会话事件（定义天然可见） | 一轮一张、两阶段切换 |
| 收尾回复的正文 | 会话快照 | `keyword` 模式扫词（复用 `src/auto.ts` 的"反向扫最长词"算法，搬到客户端） |
| 模型对 `use_sticker` 的调用（参数/结果） | 会话日志里的工具节点 | reason=`model`，尊重模型挑的那张 |
| 总开关 / 模式 / everyTurns / 缩略图等配置 | `ctx.settingsScope`（客户端本来就读得到） | 与设置面板同源，改设置即时生效 |
| 会话静音 / 冷却 `recent` / 面板 `latch` | 既有宿主状态（`state.json`）+ 一个只读小端点 | `/fish off`、不连贴同一张、"下一轮用这张"语义不变 |

⇒ **宿主不再需要"发布事件 → 客户端轮询取走"这条链**，`autoBus` / `poller` / `store` 的内存仓 / `lastSticker` 轮末刷新这一整套（v1.0 §12–§15 的事故来源）可以整体退役。

### 3.4 为什么不把决定写进会话日志（**这是硬约束，必须写下来**）

最"正统"的做法是像官方 `present` 那样 `session.append('memes-reply/sticker', …)`，让决定成为日志事实。**但这条路对本插件是危险的**：

- `Session.append(type, data, …opts)` 只能传 `surfaceOp` / `sourceEventSeqs`，**没有任何渠道设置 `ignorable` 标记**（`dsh-session/lib/index.js` 的 `append` 实现）。
- 持久化读取路径的规则是：**"类型不在本构建的已知集合里、且没有 `ignorable: true` → 拒绝解释整个日志"**（`dsh-session-persistence/lib/index.js:184` 的原文报错）。
- 已知集合 `KNOWN_SESSION_EVENT_TYPES` 是**仓库内生成**的静态表，**下游插件的事件类型按构造就不在里面**（`known-event-types.d.ts` 的注释原话）。
- 结论：**写自定义会话事件 = 让这个 session 在下次加载时变成"拒绝解释"**，代价是用户的历史会话。

所以 v2.0 明确：**只读会话事件，不写会话事件**。宿主状态（静音/冷却/指定）继续走既有的小端点，不进日志。

> 这条也是本方案"纯派生"的正当理由：派生 = 可重放 + 零日志污染 + 零时序竞态。

### 3.5 形态与动画

- 渲染：复用现有 `bubble` 的 CSS 观感与交互（圆贴纸压右下角 / 悬停放大 / 点击 `window.open` 大图），但**渲染 `url`（全尺寸动画），彻底删掉 `thumb` 回退路径**（FR3）。
- 尺寸：以设置项控制显示边长（沿用 `bubbleSize` 一类），素材 320px 满尺寸内显示。
- 性能（NFR4）：不可见（`IntersectionObserver` 出视口）时暂停/换静态帧；同屏张数上限保护。
- 占位动画同样走动画路由，D6 的"生成中"才有意义。

### 3.6 退役清单（本次删掉的东西，避免两套并存）

| 退役 | 文件/端点 |
| --- | --- |
| 气泡角链式座位 | `src/client/index.tsx` 的 `conversation.chat.turnTail` 注册 |
| 兜底浮层 | `src/client/fallback.tsx` + `shell.overlay` 的 `-fallback` 条目 |
| 轮询器与内存仓 | `src/client/poller.tsx`、`src/store.ts`、`GET /auto/pending` |
| 宿主发布链 | `src/auto.ts` 的 `AutoBus`、`src/index.ts` 的 `lastSticker` 轮末刷新、`llm/stream` 观察者（若关键词改在客户端扫） |

### 3.7 保留清单

素材路由（`/sticker/<id>`、`/thumb/<id>`、`/catalog`）· 索引与双根解析 · 模型工具 `use_sticker` · 斜杠命令 `/fish` · 设置命名空间与配置面板 · **常驻挂件 `pet`** · trace/`/stats` · 导入脚本。

## 6. 风险与局限（诚实清单）

1. **P1/P2 未验证前，方案 A 只是高置信度假设**（API 是从部署版 d.ts + 官方 deliverables/ui-chat 实现读出来的，不是跑出来的）。
2. **构建期依赖落后**（rc.8 vs 1.5-rc.1）：类型可能对不上，需要升级或就地声明；升级本身可能牵动其它客户端代码。
3. **插入节点是"改会话流的形状"**：官方有几个地方按"节点种类"做推断（skill 名批次、收尾助手是否 tail），必须靠 P2 逐项证明不影响，否则可能影响 `present`/分支这类功能。
4. **历史回合不补贴纸**：派生只对"装好之后产生的回合"生效（旧会话没有我们的节点定义数据——这是刻意的，避免改写历史）。
5. **不写日志的代价**：宿主端"我这轮到底贴了没贴"不再是一条日志事实，而要看 `/stats` 的 trace；换机器/重装插件后，历史贴纸仍能重放（因为纯派生），但 trace 是内存态。
6. **动画的内存账**：全帧 WebP 会员 560KB 均值；同屏多张必须做可见性暂停，否则长会话滚动会吃内存。
7. **CLI / headless 无渲染**：那里本来也没有客户端，贴纸只存在于 web profile（与 v1.0 一致）。

## 8. 你侧的验收清单（M2.0 完成后）

1. 连问 5 轮：每轮最终回复角上一张，中间工具步骤不贴。
2. 盯一个长回合：先「思考/打字」，回复写完的瞬间换成最终贴纸（前一张消失）。
3. `F5` 刷新：所有贴纸逐条还在，位置不变。
4. 开两个会话：各贴各的，不串台。
5. 贴纸**在动**（不是首帧静图）。
6. 回复里带文件路径（会出交付卡片）的回合：**贴纸照样在**（这条是 v1.0 的老事故，必须回归）。
7. `/fish off` 后本会话不再贴；设置里关总开关后全站不贴。
8. 右下角挂件照旧：可拖、可换、可收起。

**额外收获（写进代码注释了）**：

1. 节点对象要自己构造（官方 `chatNode()` 不导出）：
   `{key: context.key, kind, id: context.id, target:'chat', anchorSeq, location, visibility, data}`；
2. 渲染是**按 kind 字符串**分发的（`renderSlot(..., {entryKey: node.kind})`），未知 kind 不炸、
   会渲染 JSON 兜底；
3. **`assistant/live-chunk` 这类瞬时事件不喂给定义** —— 所以"生成中"的锚点只能取最后一个**持久**事件
   的 seq（`turn/start` / `step/start`），它正好在流式正文之前；
4. 定义注册**按 kind 唯一**：热更时"新的先注册、旧的还没销毁"会被判重拒绝（探针阶段踩到过，
   表现为"节点突然全没了"），所以注册要 try/catch 并把结论回传。
